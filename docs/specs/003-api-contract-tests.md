# 003 — API contract tests

**Status:** in progress · **Goal:** G2 · **Affects:** api (startup split, tests), infra (CI, Atlas test user), tooling · **Stories:** none (no behavior change)

## Why
- **Every API check is manual today.** [Spec 002](002-backend-hardening.md) was verified with hand-written `curl` scripts, and several script bugs looked like app failures at first (see its Retro).
- **The next specs change the API.** [004](../roadmap.md) replaces the validators with shared schemas, and [005](../roadmap.md) changes how payments are marked paid. Without tests, nothing shows what else changed by accident.
- **The API has no `test` script.** `apps/api/package.json` answers "no test specified", and CI only lints and builds.

## What
- Automated tests send real HTTP requests to the API and check the **contract**: status code, error code (e.g. `400 USERNAME_INVALID`) and response shape for every route.
- The tests describe the API **as it is today**, including behavior that later specs will change on purpose (the payment toggle). Those specs then update the matching tests.
- The tests use a real MongoDB on Atlas, in their own database `payflow-test`, never `payflow-dev` or `payflow-prod`.
- CI runs the tests on every pull request that touches the API. A failing test blocks the merge.

**Not included:** web app tests, end-to-end browser tests, load tests, test coverage targets, fixing the bugs the tests may find (each found bug is noted in [`architecture.md`](../architecture.md#known-issues) and goes to the spec that owns it).

## Done when
1. `npx nx test @payflow/api` passes locally against `payflow-test`.
2. Every route in [`auth.routes.ts`](../../apps/api/src/routes/auth.routes.ts) and [`installment.routes.ts`](../../apps/api/src/routes/installment.routes.ts) has tests for: success (status and response shape), missing or invalid token (protected routes), and its main `400`/`404` errors.
3. The [spec 002 "Done when"](002-backend-hardening.md#done-when) checks 1, 3, 4 and 5 (crash inputs, `INVALID_CREDENTIALS`, rate limit, CORS and headers) are automated tests.
4. Pointed at any database other than `payflow-test`, the tests stop before sending a request, with a clear message.
5. A full run leaves no test users or installments behind.
6. A pull request with a deliberately broken API response fails CI, and the merge is blocked. Then the change is reverted.

## How
- **Tools:** [Vitest](https://vitest.dev/) runs the tests (TypeScript works without extra setup) and [supertest](https://github.com/ladjs/supertest) sends requests to the app in memory, without opening a port. Both are dev dependencies of `@payflow/api`. Nx picks up the new `test` script as a target, so `nx affected -t test` works. The `test` target is **not cached**: its result depends on the database, not only on the files.
- **Startup split:** supertest needs the Express app without `listen()` and without connecting to the database. `src/index.ts` is split into `src/app.ts` (builds and exports the app: middleware, routes, error handler) and `src/index.ts` (loads `.env`, connects, listens). The Render start command (`node dist/index.js`) stays the same.
- **Database:** a separate database `payflow-test` on the same Atlas cluster.
  - Why not `payflow-dev`, as noted in the [spec 002 Retro](002-backend-hardening.md#retro): tests create and delete many users. In their own database they never mix with dev data, and the whole database can be dropped by hand if a run crashes halfway.
  - A new Atlas database user `payflow-ci` with `readWrite` on `payflow-test` **only**. Its connection string is the only one the tests read, from `MONGO_URI_TEST`: locally in the gitignored `apps/api/.env`, in CI as a GitHub Actions secret. Even a leaked CI secret cannot read `payflow-prod`.
  - **Guard:** after connecting, the test setup checks the database name and stops the run unless it is `payflow-test`.
  - Atlas Network Access is already `0.0.0.0/0`, so GitHub's runners can connect. If Atlas refuses a connection, check the access list first; it is not a test failure.
- **Test data:** every test file creates its own users with a random suffix (e.g. `t8f3a2calice`; usernames allow only lowercase letters and digits) and deletes them at the end with `DELETE /api/auth/me`, which also deletes their installments. Two CI runs at the same time never touch each other's data, so no locking is needed.
- **Secrets in tests:** `JWT_SECRET` is a random value generated by the test setup; it is not a real secret.
- **Rate limit:** the limiter keeps its counts in memory, per process. Vitest gives each test file its own copy of the app, so the rate-limit tests live in their own file, and no other file makes more than 10 sign-ups or failed logins.
- **Toggle (current behavior):** `POST /api/installments/toggle` flips whatever IDs the client sends, and skips unknown IDs without an error. The tests pin this as it is, marked with a comment pointing to [005](../roadmap.md), so 005 changes them on purpose.
- **CI:** `lint-and-build` runs `npx nx affected -t lint build test` with `MONGO_URI_TEST` from the secret. The required check stays the same. Pull requests from forks get no secrets; that is fine, because only Murad opens pull requests.
- **Rollback:** the only production change is the startup split (T1). If the API fails to start after deploy, redeploy the previous deploy in Render and revert the merge.
